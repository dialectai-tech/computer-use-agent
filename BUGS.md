### ✅ BUG-007: Empty messages after context reset
**Status**: ✅ Fixed (commits 31115d8, fd50030, 5bc50d7, 11ba1e3)
**Priority**: Critical
**Found in**: After implementing auto-reset

**Description**:
After context reset, AWS Bedrock rejected messages with error "messages.2 is empty".

**Root Cause**:
Multiple issues:
1. Screenshot stripping created empty content arrays
2. first_user_message was stored as reference and got mutated during stripping
3. Reset reused the mutated reference

**Solution**: ✅ FIXED

- Keep screenshots if message would become empty
- Deep copy first_user_message when storing initially
- Deep copy again when using in reset
- Keep last 2 messages intact during stripping

### ✅ BUG-002: Invalid CSS selectors generated by AI
**Status**: ✅ Fixed (commits 3af4656, 29748eb)
**Priority**: High
**Found in**: Iteration 2

**Description**:
AI generates jQuery-style selectors that are invalid in standard CSS/DOM APIs.

**Evidence**:
```
DOM Click: button:contains('START')
Error: 'button:contains("START")' is not a valid selector
```

**Root Cause**:
- `:contains()` is jQuery syntax, not valid CSS
- DOM manipulation tool doesn't validate selectors before execution
- AI model may be trained on jQuery examples

**Impact**:
- Wastes iterations on failed clicks
- AI gets confused by selector errors

**Solution**: ✅ FIXED
1. Added `validate_selector()` method with regex patterns
2. Detects jQuery patterns: `:contains()`, `:has()`, `:visible`, `:hidden`, `:first`, `:last`, `:eq()`, `:gt()`, `:lt()`, `:even`, `:odd`
3. Provides helpful error messages with valid alternatives
4. Updated tool description with clear examples of valid vs invalid selectors
5. Validation runs before every click_selector/fill_selector/get_info action
6. Uses negative lookahead to avoid false positives (`:first-child` is valid)

**Verification**: All 13 validation test cases passing

### ✅ BUG-003: Generic selectors cause timeouts
**Status**: ✅ Fixed (commit 3af4656)
**Priority**: Medium
**Found in**: Iteration 19

**Description**:
AI uses overly generic selectors like `input` that match multiple elements or hidden elements, causing timeouts.

**Evidence**:
```
DOM Click: input
Error: Page.click: Timeout 5000ms exceeded
```

**Root Cause**:
- AI doesn't provide specific enough selectors
- No guidance to use more specific selectors (id, classes, attributes)
- DOM Find doesn't return which selector to use, just that element exists

**Impact**:
- Wasted iterations
- Stuck loops

**Solution**: ✅ FIXED
1. `find_selectors` now returns `recommended_selector` field with best match
2. Picks best selector: ID > class > tag
3. Adds helpful summary: "Use first: click_selector(selector='...')"
4. Validation rejects generic single-tag selectors (button, input, div, etc.)
5. Provides error: "Selector is too generic, use find_selectors to get specific selector"
6. Updated tool description to emphasize using recommended_selector

**Verification**: find_selectors now returns actionable, specific selectors

## Performance Issues

### 🟡 BUG-005: Token growth still excessive despite optimizations
**Status**: 🟡 Open
**Priority**: Medium
**Analysis Needed**

**Description**:
Despite screenshot stripping and message pruning, tokens still grew from 5K to 210K over 20 iterations.

**Breakdown**:
- Iteration 1: 5,469 tokens
- Iteration 11: 82,899 tokens
- Iteration 21: 210,390 tokens
- Average growth: ~10,000 tokens/iteration after iteration 10

**Evidence of Working Optimizations**:
- ✅ Screenshots: Constant at 1,406 tokens
- ✅ System prompt: Cached (0 tokens after iteration 1)
- ✅ Message pruning: Active (kept 22 messages with 10 turns)

**Where are tokens coming from?**:
- AI Responses: Growing (208,984 tokens at iteration 21)
- Page text: 13,392 tokens at iteration 6 (sent once on navigation)
- Message pruning keeps 10 turns = 20 messages of conversation history

**Analysis**:
With 10 message turns and verbose AI responses (~2,000 tokens each at end):
- 10 turns × 2 messages/turn = 20 messages
- 20 messages × ~2,000 tokens = 40,000 tokens from responses
- But we're seeing 208,984 tokens from AI responses (5x more!)

**Root Cause Hypothesis**:
AI responses include tool_use blocks with full JSON structures that accumulate. The "AI Responses" metric may be overcounting or message pruning isn't aggressive enough.

**Solution Options**:
1. Auto-reset should have prevented this (see BUG-001)
2. Reduce max_message_turns to 3-5 (was 10 in test)
3. Investigate why AI response tokens are so high
4. Strip tool_use blocks from old messages (keep only text)

### ✅ BUG-008: Empty continuation after auto-reset  
**Status**: ✅ Fixed (commit 14c31b0)  
**Priority**: Critical  
**Found in**: After fixing BUG-007

**Description**:
Even with BUG-007 fixed, empty message error still occurred immediately after auto-reset triggered.

**Root Cause**:
After context reset:
1. `last_tool_uses` is cleared in reset_context()
2. Next iteration calls `create_continuation_request`
3. Builds `tool_result_content` by iterating empty `last_tool_uses` list
4. Appends user message with empty content array
5. AWS Bedrock rejects empty content arrays

**Solution**: ✅ FIXED
1. Added `just_reset` flag to track when reset just happened
2. After reset, start fresh iteration (take screenshot, continue normally)
3. Safety check in `create_continuation_request`: if `tool_result_content` empty, add placeholder text

**Verification**: ✅ Tested at 2026-02-08 12:32
- Auto-reset triggered at iteration 6 (20,454 tokens)
- Printed "Starting fresh iteration after context reset..."
- No empty message errors
- Continued normally for 4 more iterations

### ✅ BUG-009: Token counting uses cumulative stats instead of per-call stats
**Status**: ✅ Fixed (commit TBD)
**Priority**: Critical
**Found in**: Test run 2026-02-08 12:45:46 (after BUG-008 fixes)

**Description**:
After context reset, token display showed 217K tokens despite only 2 messages in conversation. Token breakdown showed "AI Responses: 215,723 tokens" when only ~2K tokens were actually sent.

**Evidence**:
```
Iteration 23 (after reset at iter 22 with 211K tokens):
  Auto-reset triggered successfully
  Messages cleared to 2 (first + checkpoint)
  Conversation dump: 653KB (down from 4.6MB)

Iteration 25 (first API call after reset):
  Input Tokens: 217,129  ← Should be ~5K!
  AI Responses: 215,723  ← 99% of tokens!
  Screenshots: 1,406
```

**Root Cause**:
In `loop.py:154-165`, the token extraction logic checked for `response.input_tokens` (attribute access) on the Bedrock Converse API response, which is a **dict** not an object with attributes. When attribute check failed, it fell back to `self.provider.stats.input_tokens` which contains **cumulative** totals across all API calls, not the current call's tokens.

The Bedrock response structure is:
```python
response = {
    'usage': {
        'inputTokens': 5234,
        'outputTokens': 187
    },
    # ... other fields
}
```

But the code checked:
```python
if hasattr(response, 'input_tokens'):  # Always False for dict!
    breakdown.total_input_tokens = response.input_tokens
elif ...:
    # Falls back to cumulative stats
    breakdown.total_input_tokens = self.provider.stats.input_tokens  # 2.2M!
```

**Impact**:
- Token display completely wrong after context reset
- Makes it appear that context reset doesn't work
- Auto-reset threshold logic would use wrong values (but was saved by using `breakdown.total_input_tokens` which happened AFTER the fallback)
- Debugging extremely difficult - conversation dumps showed correct data but display showed 100x inflation

**Solution**: ✅ FIXED
Added dict response check before falling back to cumulative stats:
```python
if hasattr(response, 'input_tokens'):
    # Response object with attributes
    breakdown.total_input_tokens = response.input_tokens
    breakdown.total_output_tokens = response.output_tokens
elif isinstance(response, dict) and 'usage' in response:
    # Bedrock Converse API response dict format
    breakdown.total_input_tokens = response['usage'].get('inputTokens', 0)
    breakdown.total_output_tokens = response['usage'].get('outputTokens', 0)
elif hasattr(self.provider, 'stats') and self.provider.stats:
    # Fallback: cumulative stats (should rarely be reached now)
    breakdown.total_input_tokens = self.provider.stats.input_tokens
    breakdown.total_output_tokens = self.provider.stats.output_tokens
```
